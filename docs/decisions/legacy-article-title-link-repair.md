# 旧文章 title/link 对调修复

## 问题

早期 `DBManager.save_articles` 曾将参数按 `(feed_id, link, title, ...)`
写入显式列 `(feed_id, title, link, ...)`，导致部分本地数据库中的文章标题和
链接互换。UI 的展示适配会把标题临时纠正，但正文抓取仍可能把普通标题传给
HTTP 客户端，因此 `original_html`、Cleaned HTML 和 Markdown 都无法生成。

## 迁移策略

- `DBManager.create_tables` 在同一数据库事务中执行幂等修复。
- 仅处理“`title` 是有效 HTTP(S) URL，且 `link` 不是有效 HTTP(S) URL”的
  高置信度记录，避免修改标题和链接本来都是 URL 的合法文章。
- 交换字段时保持文章 ID 不变，因此星标、标签关联和其他外键关系不变。
- 如果目标 URL 已被另一条正确记录占用，不合并或删除任何记录；保留两条记录
  及其用户状态，只重置缺失正文记录的失败状态。抓取服务会从旧记录的
  `title` 识别真实 URL，避免唯一索引冲突。
- 当文章还没有原始 HTML 时，清除旧抓取错误并将抓取状态重置为 `pending`；
  当原始内容和清洗结果都不存在时，再将清洗状态重置为 `pending`。
- 已有原始内容、清洗内容、翻译、摘要、星标和标签不会被删除。
- 正文抓取服务仍会在发起请求前规范化标题和链接，作为未迁移遗留数据的第二层
  防护。
- 抓取到的整页 HTML 只作为清洗等后台处理的输入；Reader 的“原始内容”继续
  显示 Feed 提供的正文或摘要，避免后台抓取完成后阅读视图突然改变。只有 Feed
  内容确实为空时，才使用抓取 HTML 作为可读性 fallback。

## 验证

- 自动测试覆盖旧记录修复、重复迁移幂等性、唯一链接冲突、星标/标签/翻译
  保留，以及正常 URL 标题不被误改。
- 抓取测试使用 Mock Fetcher，确保不会依赖真实网络。
- 修复真实用户数据库前必须先复制备份，并在修复后只读核对记录数量、字段方向
  和用户状态。
